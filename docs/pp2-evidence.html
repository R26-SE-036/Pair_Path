3 · How my component works

The loop, in six steps

1. TWO STUDENTS PAIR      One drives (types), one navigates (guides).
                          The navigator's editor is read-only — roles are
                          enforced by the system, not by agreement.

2. EVERY ACTION LOGGED    Edits, code runs and their results, chat messages,
                          role swaps — all written to the database as they
                          happen.

3. THE MODEL IS ASKED     Every 60 seconds, every 30 actions, and instantly
                          after a failed run. It reads the last 3 minutes
                          and computes 15 behavioural measures.

4. A STATE IS PREDICTED   One of five: productive, driver dominance,
                          passive navigator, logic struggle, disengaged.

5. AN INTERVENTION IS     Only if confidence is high enough, only if the
   CHOSEN                 same nudge has not fired in 5 minutes, and
                          addressed to the pair or to one student.

6. THE STUDENTS SEE IT    A glow, a pulse, a highlight, or a hint card.
                          Accepting or dismissing it is recorded.

The design rule behind all of it: a message says where to look and what to do differently — never how to fix the code. That is enforced by the shape of the message contract, so a solution cannot be delivered even by accident.

4 · Model, dataset and hint pipeline

The model

  • XGBoost, 5-class classifier
  • 15 behavioural features over a 180-second sliding window
  • Hyperparameters selected by grouped 5-fold cross-validation across 108 configurations — not hand-picked
  • Every trained model writes a model card: dataset, split, held-out sessions, metrics

The dataset

  • 200 sessions → 3,709 labelled windows
  • Split by whole session, never by row, so no session appears on both sides
  • Duplicates removed within sessions; class imbalance handled by weighting, not by copying rows
  • Trainer refuses to run on labels that are not human-sourced

The 15 features

GroupMeasures
Activitytotal_edit_count, driver_edit_count, navigator_edit_count, edit_balance_ratio, idle_ratio, active_user_dominance
Executionrun_attempt_count, run_success_rate, consecutive_failure_count, error_recovery_seconds_avg
Communicationdiscussion_note_count, navigator_note_count
Roles & timerole_switch_count, seconds_since_role_switch, session_elapsed_seconds

Two features carry the hardest distinctions. Navigator message count separates driver dominance from a passive navigator — both look like "one person typing"; the difference is whether the other student is talking. Seconds since role switch separates dominance from a healthy pair.

The hint pipeline (RAG-lite)

Question tags + error text + code  →  score 37 knowledge entries  →  top 3
                       (tag +5, primary topic +2, error keyword +3, code keyword +1)
                                          ↓
                     concept reminder + example idea + reflective question

Retrieval runs over a curated corpus rather than a generative model. That is a deliberate safety guarantee: no document in the corpus contains the solution to an exercise, so a hint cannot leak an answer. If nothing matches, a safe general hint is returned rather than an error.

Retrieval measured over 26 labelled casesAccuracyUnwanted fallbacks
Concept tags only69.2%6 of 24
Tags + error + code100%0 of 24

Supplying the error message is worth +30.8% retrieval accuracy. Without it, a pair hitting an array error on a question tagged modulo receives generic advice; with it, they receive the array-bounds concept. Reproducible via dev_tools/evaluate_rag.py.

The 100% is over cases authored while building the system — it shows every situation anticipated is handled, not that retrieval is perfect. Real student errors would be expected to lower it.

What precision and recall mean — in plain words

Precision — when the system says a state, how often is it right?
Passive navigator 0.897 → about 9 out of 10 times it flags a silent navigator, it is correct.

Recall — of all the times a state really occurred, how many did it catch?
Passive navigator 0.991 → it almost never misses one.

F1 — the two combined into a single score. Useful because a system can cheat on one by sacrificing the other.

Where they trade off: driver dominance has high recall (0.901) but lower precision (0.741) — it catches nearly every case, at the cost of some false alarms. Given the intervention is a gentle "consider switching roles," that is the safer direction to err in.

Metrics that do not apply, and one not yet measured

Mean squared errorN/AMSE measures error in predicted numbers. This is classification — the output is a category, not a value. Precision, recall and F1 are the correct measures.

7 · Non-functional requirements

NFRStatusEvidence
1 · Performance Satisfied Target <100 ms. Measured 1.3 ms mean, 3.0 ms at the 99th percentile — 33× inside budget.
2 · Reliability Satisfied Deterministic: identical input always gives identical output. Evaluation reproduces to the same figures. Every external dependency has a fallback — the system degrades rather than fails.
3 · Usability Not measured Designed for it — non-intrusive nudges, self-dismissing praise, no jargon, sensitive prompts sent privately. But no usability study has been conducted, so there is no score.
4 · Efficiency Satisfied 15 features, 630 KB model, ~1 ms inference. Cooldowns cap intervention frequency; the model is queried on triggers rather than continuously.
5 · Security & privacy Mostly JWT verified on both REST and socket handshake; identity taken from the token, never the message; session membership enforced on every action; student code runs in an isolated container with no network.
Outstanding: ethical clearance before real data collection.
6 · Interoperability Ready REST + JSON throughout, documented endpoint and event contracts, service-to-service over HTTP. Ready for integration but not yet demonstrated with sibling components.

9 · Summary for the panel

Complete

  • Real-time collaborative editor with enforced roles
  • Full behavioural instrumentation — seven event types
  • Five-state classifier, evaluated on unseen sessions
  • Confidence-gated, cooldown-limited interventions
  • Role-addressed delivery for sensitive prompts
  • Hint retrieval that cannot leak solutions
  • Sandboxed code execution and authenticated sockets
  • Post-session peer review with scoring
  • Reproducible training and evaluation pipeline

Remaining

  • Integration with the three sibling components
  • Peer review quality assessment
  • Line-based review comments
  • Usability study
  • Ethical clearance
  • Classroom study — objectives 4 and 5

Two things worth saying before you are asked.

1. Driver dominance and passive navigator were initially defined so similarly that no classifier could separate them. Redefining dominance as an engaged navigator who never receives the keyboard — which also matches the intervention each triggers — raised overall F1 substantially. That is a finding about how collaboration states should be defined, and it is arguably the most transferable result here.

2. Objectives 4 and 5 are deliberately future work. They require a classroom study, which requires ethical clearance. Naming that as a planned phase is stronger than implying it is done.

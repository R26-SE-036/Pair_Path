Hint Engine Roadmap

The retrieval chain is built and working. What's missing is that it runs on a third of the signal it was designed for, from a library of nine entries, with no way to tell whether a hint was any good. Five phases, roughly a day of work, ordered by value per hour.

What already works — don't break it

No corpus document contains a solution. That's an architectural guarantee, not caution while writing. Every phase below must preserve it.

The three-part output holds: concept reminder, example idea, reflective question. Keep that contract stable so the frontend and the paper both stay valid.

It degrades safely. Nothing matched still returns a usable hint with fallbackUsed: true rather than an error.

1

Send the error and the code

Start here ~30 min

The problem The gateway hardcodes two empty strings, so the +3 and +1 scoring paths in your retriever can never fire. Only tag matching works. 

// websocket.gateway.ts — today
recentErrorContext: '',
recentCodeSnippet: '',

The fix Keep the last failed run's stderr and the current code in the session, and pass them through. Both are already available where the run result is handled.

Your corpus was designed for this. The keywords are written without spaces — outofbounds, nullpointer, offbyone — which is exactly how they appear inside a Java exception name. Someone wrote them to match real error text, and that text never arrives.

What changes A student hitting ArrayIndexOutOfBoundsException gets the array-bounds entry because the error matched, not because the question happened to be tagged correctly. Hints stop being per-question and start being per-situation.

2

Let the library grow

~1 hour

The problem knowledge_loader.py reads one Content: line per file and overwrites earlier ones. Nine files means nine entries, and adding a hint means adding a file.

The fix Support multiple entries per file, separated by a blank line or a marker, and carry the hint text with the entry instead of generating it from a template: 

Tags: arrays, indexing, bounds
Keywords: array, index, outofbounds, length
Content: Java arrays start at index 0, so the last valid
  index is array.length - 1.
Example: Check whether your loop condition uses < or <=.
Question: If an array has N elements, what is the highest
  valid index you can access?
---
Tags: arrays, iteration
Keywords: array, loop, sum, accumulate
Content: ...

Then fill the gaps Your questions use bounds and modulo; neither matches anything, so those students get a hint that is true of every program and useful for none. Aim for 25–30 entries covering every tag your question bank actually uses.

This phase is mostly writing, not coding — and it is the part that decides whether a stuck student gets something specific or something generic.
3

Write the hints properly

~1 hour

The problem Only four topics get tailored wording — loops, arrays, collaboration, peer review. Everything else is assembled from a template: 

example_idea = f"Review your code handling {topic}. Are you
  sure the logic aligns with the core rule?"

That sentence is grammatically fine and pedagogically empty. It's the same advice whether the student is confused about methods, conditions or types.

The fix Once entries carry their own Example: and Question: (Phase 2), hint_generator.py mostly stops generating and starts assembling. The special-case if chain disappears — every entry brings its own wording.

A good reflective question is written by a person who understands the misconception. It cannot be produced by string formatting, and it should not be produced by a model at runtime — see the warning below.
4

Measure retrieval

For the paper ~1 hour

The problem You cannot currently say anything quantitative about the hint engine. It either returns something or falls back — and you have no idea how often it returns the right something.

The fix A small labelled test set — 20 to 30 cases of (error text + question tags) → the entry that should come back — and a script that reports two numbers:

MetricQuestion it answers
retrieval accuracyHow often is the top result the right one?
fallback rateHow often does nothing match at all?
This is the phase I'd argue hardest for. Your proposal defers embeddings to Phase 3 as "a scored comparison against the RAG-lite baseline." You cannot score that comparison later unless you can measure the baseline now. Without it, the upgrade becomes "we swapped it and it felt better," which isn't a result.

It also puts the hint engine on the same footing as the classifier: a component you evaluated, not just a feature you built.

5

Escalating hints

~2 hours · optional

The idea Real scaffolding fades. A pair stuck on the same error for the third time needs something more direct than the first nudge — while still never receiving the answer.

Count how many hints a session has already had for the same concept, and step through levels: reflective question → concept reminder → worked analogy on a different example.

This is genuine pedagogical design and would strengthen the dissertation, but it needs the earlier phases first — there's no point escalating between hints that are all generic.
6

Embeddings — deliberately last

Phase 3 of the research

Why not now Not only because your proposal defers it. At 25 entries, embeddings would barely differ from keyword matching. They earn their keep across thousands of documents where wording varies; over a small hand-curated corpus with deliberate tags, keyword scoring is competitive and fully explainable — you can point at exactly why a hint was chosen.

When you do it The RAGChunk.embedding column already exists in your schema. Run the Phase 4 test set against both retrievers and report both numbers. Keep the output contract identical so only retrieval changes.

"We compared embedding retrieval against a keyword baseline and it did not justify the added opacity" is a legitimate, publishable finding — if you have the numbers. Phase 4 is what makes that sentence possible.

Do not generate hints with an LLM at runtime

It is the obvious "upgrade" and it would quietly destroy your core guarantee.

It leaks solutions. Your entire safety argument is that no corpus document contains an answer. A model generating text on the fly can produce one at any time, and no prompt reliably prevents it. The guarantee stops being architectural and becomes a hope.

It breaks reproducibility. The same student in the same state gets different help on different runs. You could not report what your system does, only what it did once.

It adds latency and cost to a path that currently answers in milliseconds during a live session.

Retrieval over curated text is the right architecture here. The upgrade is a better corpus and better measurement — not a generative model.

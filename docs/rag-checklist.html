Embedding comparison

Research phase 3 Later

Deliberately last. Over a small hand-curated library, keyword scoring is competitive and fully explainable — and group 4 is what lets you prove that rather than assert it.

RAGChunk.embedding already exists in the schema and is unused.
The output contract must stay identical so only retrieval changes.
Same cases, same metrics, one table.
"Embedding retrieval did not justify the added opacity" is a legitimate published finding — but only with numbers behind it.

One thing not to do: generate hints with a language model at runtime.

It is the obvious upgrade and it would quietly destroy the guarantee the whole design rests on. Your safety argument is that no document in the library contains an answer — a model writing text on the fly can produce one at any moment, and no prompt reliably prevents it.

It also breaks reproducibility, since the same student in the same state would get different help on different runs.

If you only do two groups, do 1 and 4.

Group 1 makes hints respond to what the student is actually looking at. Group 4 makes them measurable — and is what allows the embedding comparison to be a result rather than an impression.

Groups 1 to 4 are about a day's work and take the hint engine from "it works" to "it works well, and here is how well."
